# ADR-0002：为何 H5 子包更新与整包升级拆成两条独立链路

- 状态：已接受
- 日期：2026-10-13
- 决策人：基座维护团队

## 背景

基座承载 H5 业务，两类变更节奏完全不同：

- **H5 业务变更**：高频（可能日发多次），需要秒级回滚能力与灰度控制；
- **基座/原生变更**：低频（周/月级），受应用市场审核约束，无法即时回滚。

若共用一条升级链路，H5 高频发布会污染原生版本管理；原生强更会阻塞 H5 热修。

## 决策

两条链路独立实现、独立状态机、独立配置：

1. **H5 子包远程更新**（`src/updater/`）：
   manifest → 检查（灰度/兼容性）→ 下载 → 校验（SHA-256 + 签名策略，见 ADR-0004）→ 安装 →
   原子激活（冷启动生效，规范 §38）→ 冒烟测试 → 失败自动回滚（连续回滚上限 `UPDATE_MAX_ROLLBACKS`）；
2. **整包 APK 升级**（`src/bridge/modules/update.ts` + 原生 adapter）：
   走应用市场/安装器，签名校验由系统保证。

两者通过 `bridgeVersion` / `minAppVersion` 协商兼容性，互不阻塞。

## 后果

- ✅ H5 热修可分钟级到达用户且可回滚熔断；原生发版节奏独立；
- ⚠️ 需维护两套版本协商语义（`BRIDGE_VERSION` / `APP_VERSION`），协议演进须同时评估两侧。
